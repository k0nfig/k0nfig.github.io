Offset vs. checkpoint pagination

Two ways to fetch the next page, what happens when the data changes between requests, and how to choose between them.

Adithya

On this page

Offset pagination Checkpoint pagination When rows change ULIDs as sort keys DynamoDB pagination Counting filtered results Which one to choose

Say you’re building an activity feed that shows three events at a time, newest first. Page one returns events 106, 105, and 104. When the reader asks for more, the request can tell the database to skip the first three rows or to continue after event 104. Both return the same rows while the list stays put. Add one event at the top, and they diverge.

Offset pagination skips a number of rows

Offset pagination turns a page number into a row count. With three rows per page, page two is LIMIT 3 OFFSET 3. The database orders the results, skips three, and returns the next three.

SELECT id, created_at
FROM events
ORDER BY created_at DESC, id DESC
LIMIT 3 OFFSET 3;

The appeal is direct navigation. If a user wants page 12, the API can calculate its starting offset without loading pages 1 through 11. The database still has to work through the skipped rows, so deep offsets can be expensive even when an index supplies the ordering. [PostgreSQL on LIMIT and OFFSET]

Checkpoint pagination resumes after a sort key

Here, a checkpoint is the sort key of the last row returned. This query pattern is also called keyset or seek pagination. An API usually hands the checkpoint back as an opaque cursor. A cursor is the token sent over the wire and can also encode an offset, so a parameter named cursor tells you little about the query underneath.

The diagram labels rows by ID. The SQL uses both created_at and id because multiple events can share a timestamp. Assume created_at is non-null and id is a unique primary key. The first request omits the filter, and subsequent requests bind both values from the last row they received.

SELECT id, created_at
FROM events
WHERE (created_at, id) < ($1, $2)
ORDER BY created_at DESC, id DESC
LIMIT 3;

PostgreSQL compares the timestamps first and compares the IDs when the timestamps tie. The strict < places page two on the older side of the boundary and excludes the boundary row itself. A matching B-tree index on (created_at, id) can support a backward range scan starting at that boundary. With real workloads, check the query plan with the filters and joins the endpoint actually uses. [PostgreSQL row comparisons, indexes and ordering]

To return a hasMore flag, request one extra row and return at most the page size. If the extra row exists, build the next cursor from the last row actually sent to the client. Using the extra row as the checkpoint would skip it. Keep the cursor tied to the same filters and sort order so the next request continues the same query.

What happens when rows change?

Suppose the reader already saw 106, 105, and 104. Then event 107 arrives at the top. The offset still skips three rows, but event 104 has moved to fourth place. The checkpoint still divides the list at event 104.

Start over and delete 106 after page one. The first three rows are now 105, 104, and 103. Offset pagination skips all three, so the reader never sees 103 during that traversal. The checkpoint still starts with 103.

A checkpoint gives you a boundary. A snapshot fixes the view.

In the insertion example, event 107 sits on the newer side of the boundary and won’t appear as the reader continues toward older events. An event inserted on the older side can still show up. If a sortable field can change, a row can move across the boundary and be missed or repeated. A feed can often accept those semantics. An export that promises a consistent view needs an explicit snapshot or a materialized result set.

In PostgreSQL, successive reads within one REPEATABLE READ transaction can share a snapshot. Separate HTTP requests that open their own transactions get separate snapshots by default. Elasticsearch exposes the same distinction through search_after for position and a point in time for a consistent search view. [PostgreSQL transaction isolation, sharing a PostgreSQL snapshot, Elasticsearch pagination]

When a ULID can replace the two-column sort key

A ULID encodes a millisecond timestamp followed by a random component. Canonical ULID strings sort by that timestamp when compared in ASCII order. If the feed can use the time encoded in the ID and the database enforces uniqueness, the ULID can serve as both the sort key and the checkpoint. [Canonical ULID specification]

SELECT id, created_at
FROM events
WHERE id < $1
ORDER BY id DESC
LIMIT 3;

Here, id is a PostgreSQL text primary key storing uppercase ULIDs with COLLATE "C", and $1 is the last ULID returned. Both the range comparison and the sort use the column’s collation. You can also use ORDER BY id DESC LIMIT 3 OFFSET 3 with these same IDs. That query still skips three positions, so the insert and delete examples still apply. [PostgreSQL collation support]

Within a millisecond, ordinary ULIDs sort by their random suffix. That gives you a stable order for paging, though it can differ from the order in which the events happened. Monotonic generation can preserve generation order within the same millisecond for a single generator. Across writers, clock skew and delayed writes can put a new row anywhere relative to an existing checkpoint. Keep (created_at, id) if the feed must sort by the event’s recorded time. [ULID monotonicity]

DynamoDB continues from a key

Amazon DynamoDB is a NoSQL database whose Query API uses continuation keys. For an activity feed, you could query one account’s partition and use a ULID string as the sort key. Set ScanIndexForward to false for descending order. DynamoDB’s string sort compares UTF-8 bytes, so uppercase ULIDs retain their lexical order. [DynamoDB Query API]

When a response includes a LastEvaluatedKey, send that key back as ExclusiveStartKey with the same query. Your API can wrap it in an opaque cursor. DynamoDB provides no native offset or page-number jump in Query. To emulate “page 12” without a saved boundary, the application would have to walk through earlier results and discard them. [DynamoDB query pagination]

The key marks the last item DynamoDB evaluated, which may differ from the last item your reader saw. DynamoDB applies the query’s read limits before applying FilterExpression, so a response can have zero matches and still have a continuation key. If your API needs a page of 20 matches, set each request’s Limit to the number of slots still open. Keep querying until the page fills or the response has no continuation key. That way, the cursor never moves past a match you fetched but didn’t return. [DynamoDB query pagination]

Count all matches when the interface needs a total

A checkpoint tells you where to resume. For the SQL example, the extra-row check is enough to decide whether to show “Load more.” An exact “87 matching events” needs a count of the entire filtered result. That applies to both pagination methods.

Suppose a feed shows only failed events for one account. Use those same account and status predicates for the count. Leave out the checkpoint predicate, which would count only events beyond the current page boundary.

SELECT COUNT(*) AS total_matches
FROM events
WHERE account_id = $1
  AND status = 'failed';

An exact count can do considerably more work than fetching one page. If the count and the page must describe the same point in time, run both reads against a shared snapshot. Otherwise, a concurrent insert or delete can make the two responses disagree. [PostgreSQL aggregate functions, transaction isolation]

In DynamoDB, use Select: "COUNT" with the same key condition and filter. The count is per response, so start from the beginning and add up each response’s Count until the continuation key runs out. Returning just the count still consumes read capacity for the items evaluated. On a changing dataset, those separate requests can observe changes as they go. [DynamoDB Query API]

Choose based on how people navigate

Numbered pages
Use offset for a modest admin table when people jump directly to a page and deep queries are uncommon. Check the cost at the deepest page you plan to support.
Feeds and timelines
Use checkpoint pagination when users mostly select “Load more” and new rows arrive regularly. Pick a stable sort key and add a unique tiebreaker.
Consistent exports
Define which snapshot the export represents. Then use a checkpoint inside that stable view to read it in batches, where the storage system supports it.

Jumping straight to page 12 is simple with an offset. A checkpoint needs an existing boundary for that page. For a “Previous” button with checkpoints, retain earlier cursors or implement a reverse query from the first row of the current page.
