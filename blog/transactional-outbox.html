The transactional outbox pattern

Save the event with the change that produced it, then publish it from a worker that can retry.

AdithyaDraft

On this page

The dual-write problem The database transaction Publishing and retries Duplicates and ordering When to use it

An order can be paid without shipping hearing about it

An order service marks order 42 as paid in PostgreSQL. It then publishes an OrderPaid event so a fulfillment service can create a shipment. If the process crashes after committing the update and before the broker accepts the event, the order is paid and fulfillment has nothing to process.

Publishing first opens the opposite failure window. Fulfillment can receive the event even if the order transaction later rolls back. The order service has two independent writes, and either can succeed on its own. With a transactional outbox, the order update and the record of the event commit in the same database transaction. [AWS transactional outbox guidance]

Commit the order and its event together

The outbox is a table in the order database. Each row has a stable event ID, a type, the order ID, and the data the consumer needs. In this PostgreSQL example, $1 is the order ID and $2 is an application-generated event ID. The outbox table uses event_id as its primary key.

WITH paid_order AS (
  UPDATE orders
  SET status = 'paid'
  WHERE id = $1 AND status = 'pending'
  RETURNING id
)
INSERT INTO outbox (event_id, event_type, order_id, payload)
SELECT $2, 'OrderPaid', id, jsonb_build_object('order_id', id)
FROM paid_order;

The statement inserts an event only when the order changes from pending to paid. If the event insert fails, the update rolls back with it. If the order is already paid, the statement changes zero rows and emits no second event for that transition.

Publish separately and plan for retries

A polling worker reads pending outbox rows in batches. It publishes each event and marks the row sent after the broker confirms acceptance. With several workers, claim a batch in a short database transaction. PostgreSQL’s FOR UPDATE SKIP LOCKED lets workers skip rows being claimed elsewhere. Store a claim that expires if the worker dies so another worker can retry without holding a database transaction open during the network call. [PostgreSQL locking clauses]

Change data capture (CDC) is another way to run the relay. A connector such as Debezium can read outbox inserts from the database’s change log and route them to Kafka. Polling requires a worker and periodic reads. CDC requires a connector, recoverable offsets, and enough change-log retention for it to catch up after downtime. [Debezium Outbox Event Router]

Deduplicate by event ID and order by business key

Fulfillment can save the event ID in a processed_events table with a unique constraint. Insert that ID and create the shipment in the same local transaction. If the ID already exists, skip the shipment insert. Acknowledge the broker message after the transaction commits, so a crash before commit leaves the message available to retry. If the consumer calls an external shipping API, use the event ID as that API’s idempotency key where supported.

Some events also need to arrive in sequence. An OrderCancelled event may need to follow OrderPaid for the same order. Use the order ID as the message key when the broker supports per-key ordering, and have the relay publish those events in sequence. Sending both events to the same Kafka partition won’t fix a relay that publishes them out of order. If gaps matter, include an order version so the consumer can detect a missing earlier event. [Debezium’s outbox example]

When the outbox is worth operating

Use it when another system needs to hear about a committed change even if the broker is briefly unavailable. The order service can return success as soon as the database commits. Fulfillment catches up when the worker can publish again, so the order may be visible before the shipment exists.

The relay also needs monitoring. Track the age of the oldest pending row, failed attempts, and backlog size. A message that keeps failing needs a way to be investigated and replayed. Give sent rows a retention policy and keep consumer deduplication records long enough to cover the replay window. If every required effect fits in one database transaction, that transaction can handle the whole operation.
